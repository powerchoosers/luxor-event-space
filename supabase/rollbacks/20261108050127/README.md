# Manual bill AI recovery rollback

These files are an **operator-run contingency**, not forward migrations. Do not apply them as part of a deployment. They target the recovery migration `20261108050127_luxor_manual_bill_due_queue.sql` at SHA-256 `06c15a5ed07050f7566228d2466ec7f8ff3fe00df6e4bff9bab403de93695ebc`. Verify the target Luxor project, actual applied schema, backups and active application versions before use. Use a privileged database session with normal trigger enforcement (`session_replication_role = origin`). Never bypass the pause trigger.

1. Stop scheduling the new manual-analysis recovery callback and run `01_pause.sql`. This serializes installation against bill writes and blocks new manual-analysis processing claims, including claims from either application version. Existing provider calls may finish and write a completed or failed result. Manual analysis is unavailable during this pause; the older interface may not clearly report the pause.
2. Inspect manual bills whose `extracted_fields.manual_analysis.status` is `processing`, including paid or archived bills. Wait for real completion. Do **not** infer safety from a timeout, an expired lease, or a missing lease. If a row remains, investigate whether the provider call is actually finished; the legacy writer did not retain a provider request ID. There is no approved audited reset for uncertain work. Leave the barrier in place and stop if safety cannot be established. `02_remove_queue.sql` takes a write-blocking table lock and refuses to run while any such row remains or the barrier is disabled. It removes the queue RPCs, queue indexes and original lease gate, and deliberately retains the RLS-protected scan-cursor table and row. Bills, payment records, AI state and history are not deleted or rewritten.
3. Deploy the intended older application and cron code through the coordinated release process. Verify that **all** newer web and worker instances have drained and cannot issue new provider calls; the database cannot verify application deployment state. Confirm there are no external/in-flight provider calls and no processing rows. Only then may an authorized operator run `03_resume_after_verified_writer.sql`, which rechecks the barrier, queue removal and absence of processing records before lifting the barrier. Never run it merely because a fixed time has elapsed. Queued analyses will not have the new scheduled recovery after this rollback; owners may need to retry through the older workflow.

If any step fails, stop; transactions roll back and the pause barrier remains in effect after step 1. The retained cursor table means a later reintroduction of this exact migration needs an explicit forward migration that reuses or safely manages that state. A resume script cannot itself prove all app instances have drained, nor prove the state of an external provider request. Those are mandatory operational checks, not guarantees provided by SQL.
