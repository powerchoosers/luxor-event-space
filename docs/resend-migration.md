## Implemented foundation

- Provider selection for ordinary mail and queued email/agreement delivery, preserving the approved sender allowlist.
- Resend calendar delivery uses one named `.ics` attachment through the Email API with an explicit `text/calendar; method=REQUEST` content type. This follows Resend's iCalendar example and avoids Nodemailer's duplicate calendar parts. The delivery retains the event UID and revision timestamp for retries; delivered Outlook/Gmail rendering still requires a live verification.
- Durable outgoing records before sending, provider idempotency keys, attachment archiving, ambiguous-delivery state, and protection against late send responses overwriting webhook delivery status.
- Signature-verified webhook ingestion into a durable retry queue; incoming bodies and attachments are fetched through the authenticated Resend API and saved privately.
- New mailbox message reading, attachment downloads, reply threading, legacy stored-history display, and incoming notification integration.
- Account-wide webhook filtering to approved Luxor addresses. Other domains in the connected Resend account must not be imported into Luxor.
- Production calendar revisions saved atomically with delivery jobs: stable UID, monotonic sequence, immutable timestamps, removed-attendee cancellations, superseded-job guards, and bounded retries. New Resend events stay on their original provider even during a global mail-provider rollback.
- Resend tour scheduling now commits the event, native invitation jobs, frozen branded confirmations/reminders, response link, and inquiry tour state in one transaction. Exact retries reuse the saved jobs; obsolete queued notices are cancelled and already-claimed notices are checked again before sending.
- Raw incoming MIME is archived privately; strict calendar REPLY parsing and aligned DKIM verification protect automatic RSVP updates. Unsigned matching responses are saved for owner review rather than trusted automatically. Settings now has an explicit attendance/dismissal review dialog and required note; rendered QA remains pending.
- Incoming notification stages are checkpointed; failed push deliveries retry after the inbox record exists. Queue health identifies the active provider and retains the authenticated no-send health path.
- Archived incoming mail has server-persisted read/unread state with authenticated, same-origin mutation checks. Outbox labels distinguish acceptance, delivery, suppression, and uncertainty; refreshing the mailbox also updates the cached reader's status. Thread reads batch attachment metadata and keep raw MIME hidden.
- Per-message Zoho import preserves original MIME privately, sender names, reply headers, exact provider IDs, original thread identity, dates, and attachments. Partial imports stay hidden until all parts are saved; retries reuse completed work. A separate read-back check verifies every stored object's size and SHA-256 against its manifest and invalidates stale verification on failure. Legacy email URLs resolve to completed imports; ordinary replies stay on Zoho until provider cutover. Source folder/read-state and archive-part pagination have no 1,000-item cap.
- Resumable history runs persist folder snapshots, page cursors, per-message progress, source conflicts, retry backoff, and processing leases. Page inventory and cursor updates are atomic; expired/paused workers cannot commit progress. The worker archives or verifies at most one MIME part per request. Verification manifests use POST-body compare/swap rather than potentially oversized URL filters. New bulk imports stay staged and excluded from the live mailbox until reconciliation. No real history import has been started.

Fourteen migrations have been applied to the Luxor database: the server-only mailbox tables/private storage bucket, restriction of the existing arbitrary-SQL RPC to `service_role`, calendar lifecycle tables/functions/queue constraints, private import progress tables/functions, repeatable source comparison passes/observations with atomic import controls, current-source content audits, version-preserving source changes, owner calendar-response review, atomic tour notifications, reviewed history release, full-history mailbox paging, private campaign delivery/suppression reconciliation, atomic internal inquiry notification jobs, and all-hours transactional receipt claims. Calendar and import transaction tests ran as `service_role` and rolled back all fixtures. Verified all calendar/import tables have RLS and no anon/authenticated access; their functions are invoker functions executable only by the service role (and database owner). Do not add public storage policies for mail.

### History import controls (staged)

`GET /api/portal/mail-import` returns an authenticated, no-store summary. `POST` requires the signed portal session, same-origin JSON, and one action: `start`, `step`, `pause`, `resume`, `retry_failed`, `compare_source`, or `check_source_content`. Start additionally requires `confirm: "archive-zoho-history"`. It inventories folders but does not import bodies until subsequent `step` requests. Each step processes one source page, one closing folder check, one archive/verification part, or one current-source checksum. No cron has been enabled for these runs. Pausing retains an in-flight lease; resume waits for it to expire. Five consecutive failures isolate an item or pause the run. Controls now serialize through a private database function using the worker's run lock. `retry_failed` requires a paused/review run with no unfinished source inventory/content check and does not reset verified items.

The archive pass ends at `review/reconcile`, never automatic cutover. `compare_source` starts an explicit fresh, account-verified folder inventory. Each generation saves separate page cursors and observations, detects repeated IDs even when identical, and rechecks folders after paging. It reports added/missing/moved/changed messages against the original inventory on the first pass and the previous pass thereafter. New IDs join the existing bounded archive queue.
