## Traced schedule details

- Final-balance email milestones are selected by `queueUpcoming60DayInvoiceReminders` in `src/lib/luxorEmailJobsServer.ts`: `payment_request`, `14_days`, `7_days`, and `due_date`. The code checks for a signed contract, recorded deposit, a payable balance, and an eligible lead before creating a checkout-backed message. A manual `final_payment_reminder` can share the job type, so the milestone must match the scheduler before attributing it to this automation.
- Installment reminders require both installment feature gates, and use `installment_7_days_before` and `installment_1_day_overdue` at 10 a.m. Chicago time. The scheduler cancels queued notices when payment or a changed schedule makes them obsolete. These checks and the secure checkout behavior must remain intact when editing is added.
- The event emails are created on transitions: completed planning creates `event_details_reminder` 14 days before and `event_day_reminder` 2 days before, only when their computed times are future; completing the event creates `post_event_follow_up` 24 hours later. The current code computes the pre-event times using a fixed `-05:00` offset. Do not describe those times as a year-round Chicago local time without further verification. The local email worker checks the saved event date and booking status immediately before delivery and stops stale reminders. Local migrations add a booking-locked cancellation/replacement RPC and a transactional retry marker; the email cron retries pending generations and cannot acknowledge a newer one by mistake. Synthetic tests cover the trigger, retry marker, date and recipient fencing, idempotency and past windows. The migrations are not installed, production execution is unverified, and the send-time check cannot make external delivery and booking updates atomic.
- The unscheduled tour-request receipt is a separate `tour_confirmation` email created without a calendar revision. The scheduled tour notices carry revision and notice identifiers. Treating every `tour_confirmation` as a calendar notice would send Elena to the wrong editor.
- Offer reminders originate in two package/proposal send branches and are scheduled only when an expiration exists: approximately 24 hours after send and four hours before expiration, filtered to future times before the deadline. The first branch uses `proposal_payment_reminder`, the second uses `proposal_view_reminder`; both carry `offer_reminder: true` and an invoice ID. Each is AI-generated with an approved fallback when queued, so a future copy editor must identify these messages by origin metadata and explain that queued messages retain their snapshots. The same `proposal_payment_reminder` type also represents separate payment requests sent 72 hours later; it must not be attributed to the offer editor based on job type alone. Existing expiry checks run only when expiry metadata is present. Locally, invoice or payment read failures now hold and retry these checked messages rather than assuming the payment lookup returned no payments. This has only synthetic test coverage; real queue and provider behavior remain unverified.
- The worker rebuilds an offer reminder associated with a deposit invoice as a payment reminder after requiring a signed agreement and refreshing the balance and checkout link. Local offer overrides now carry a copy snapshot through that rebuild; otherwise the previous AI-generated payment copy remains in use. The separate 72-hour payment-request reminder also goes through this rebuild. Its local copy settings and both queue paths now snapshot custom wording and preserve it during the rebuild; the local builder, contacts view and recorded-message attribution now use a dedicated origin marker; older unmarked messages remain unattributed. Installed schema and end-to-end verification remain outstanding. Manual reminders and offer jobs use separate identification.
