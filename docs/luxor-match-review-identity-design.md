# Financial review identity boundary

Status: design only. Accounting setup writes, statement-import writes, and recorded match reviews remain disabled; this does not change access, credentials, or production configuration. The existing SQL drafts must not be applied or granted as written. A review choice is not a verified settlement, a bank reconciliation, or a journal entry.

## Current constraint

Luxor's portal session is an application-signed cookie containing an email and timestamps, with no per-session ID that the database can independently verify. The server can validate the cookie and look up the member, but the database currently receives requests through a shared service credential. The repayment review prototype improves revocation ordering by locking the member row, yet the RPC receives `p_actor` and timestamps from that same credential. A holder of the credential can claim another actor. The Phase 7 setup and import drafts use the same application-supplied attribution. Membership checks and row locks do not prove who signed the request. Development convenience sessions must never authorize sensitive actions.

## Proposed boundary

1. Keep the Zoho allowlist and existing portal access intact while the identity approach is evaluated. A sensitive database write must arrive through an independently verified, per-user authentication context. Do not accept an actor, role, session ID, timestamps, or JWT claims supplied as ordinary RPC arguments or from mutable user metadata.
2. Candidate approach: use a user bearer token verified by Supabase's supported authentication gateway, and forward that actual user token rather than a shared service token. The database derives the actor from the gateway-verified issuer and subject. Map the pair to exactly one immutable Luxor member ID through a separately controlled onboarding process; do not link accounts by email alone. Restrict accepted issuers and audiences. Supabase Auth UUID subjects can use `auth.uid()`; a third-party subject may not be a UUID and would need issuer-qualified text claims instead. Verify Zoho compatibility, token claims, issuer, role, and session semantics before selecting this approach; no provider is assumed configured.
3. A database transaction must derive the principal from verified request context and lock the authoritative member, authorization, and revocation/session records in a documented order. It must require an active owner or administrator with finance permission, a valid bound session, and a single-use explicit confirmation bound atomically to the principal, session, action, target, revision, and evidence digest. It must recheck expiry after any wait immediately before insertion. Define the authorization linearization point and the policy if a token expires after that check but before commit; a pre-insert check alone does not prove validity at commit. A revocation or permission downgrade must update or delete the same locked authority records so that a committed revocation precedes and blocks subsequent writes.
4. For Supabase Auth, investigate a protected check of the token's session ID against `auth.sessions` for immediate sign-out handling. For third-party identity, an equivalent authoritative, transactionally ordered session/revocation mechanism is required; do not assume `auth.sessions` covers it. If current session status cannot be verified, fail closed. Short token expiry alone is not immediate revocation.
5. Expose only narrowly scoped, reviewed operations for setup, import, and match review. Match review must preserve the expected revision, one-source-per-active-choice constraint, duplicate acknowledgement, exact-match and correction rules, and append-only history. Derive the audit actor from the authenticated context inside each operation. The shared service role must not be able to invoke or bypass it by supplying actor claims; no direct untrusted SQL path may be able to forge gateway request context. Gateway claims are trustworthy only if the request actually passed the verifying gateway; SQL clients that can set request claims must be excluded. A `SECURITY DEFINER` implementation, if required, needs a separately reviewed privilege boundary and must not be publicly callable by default. Inspect default privileges, ownership, bypass-RLS roles, and direct connections; removing an explicit grant alone does not prove isolation.
6. A timeout or missing session/member/evidence state is unknown, not authorization. Fail closed. Preserve idempotency by binding a request ID and immutable request digest to the derived principal; a different principal cannot replay or retrieve another principal's result as their own.

## Required verification before enabling

- In an isolated database, verify the actual gateway rejects tampered signatures, wrong issuer or audience, missing/expired tokens, and role or claim substitution. Verify a shared service credential cannot invoke the operation or forge another actor through database request-context settings or direct SQL.
- Verify valid users cannot submit `actor`, `member`, `role`, or session claims to impersonate another user. Verify same request ID with a different authenticated principal or payload conflicts without disclosing another user's record.
- Race a valid write against suspension, finance-permission removal, session revocation/sign-out, and token expiry while the write waits on a lock. Check which transaction committed first; once a revocation commits, subsequent writes must fail and create no event. Test the approved expiry linearization policy, including expiry after the final check but before commit.
- Race two selections for the same row and two different rows for the same source; exactly one may succeed. Confirm stale revisions fail, corrections append rather than overwrite, missing account/currency evidence remains unverified, and no transaction or journal is created.
- Verify actual grants, RLS, function execute privileges, identity-binding maintenance, key lifecycle, direct connection restrictions, monitoring, and rollback in the intended deployment environment. Synthetic unit tests cannot prove these controls.

## Decisions still required

- Whether an approved Zoho-backed identity can provide a supported, per-user, gateway-verifiable token and immediate revocation, or whether a different user-authentication bridge is required. Do not change the current approved-email access model until that is resolved.
- Who may establish or revoke issuer/subject-to-member bindings, and how duplicate identities, account recovery, offboarding, and existing sessions are handled without takeover or access loss.
- The precise confirmation, reauthentication, session lifetime, and revocation policy for sensitive financial reviews, plus a reviewed database privilege model and rollout/rollback plan.
- Accountant decisions on source-account evidence, currency, deposits, fees, split/partial matches, and reconciliation. A human attestation remains an attestation until independently verified.
